## Врезка 1 — накопитель текущего хода, доступный по id вызова

Место (2.1.235, дословно):

    if(po.type==="assistant"){if(ne&&Ruf(Z.agentId,Z.agentContext)&&!po.isApiErrorMessage)xuf(po.message.content);
    let Dl=Jc??po;if(!Ju)Ye.push(Dl);let Xu=Dl.message.content.filter((wd)=>wd.type==="tool_use");

Факты, на которых стоит врезка:
- в стриминге КАЖДЫЙ блок содержимого выходит ОТДЕЛЬНЫМ сообщением
  ассистента (`content: UKn([ni], ...)` — массив из одного элемента),
  поэтому сообщение, доезжающее до исполнителя, несёт ТОЛЬКО блок
  вызова инструмента, без рассуждений;
- накопитель (`Ye`) собирает ВСЕ сообщения ассистента текущего хода,
  включая блоки рассуждений (они копятся открытым текстом).

Правка: перед `addTool` положить СНИМОК накопителя в глобальную карту,
ключ — id блока вызова:

    globalThis.__ccJudgeTurn ??= new Map();
    globalThis.__ccJudgeTurn.set(wd.id, Ye.slice());

Почему карта, а не поле контекста: объект контекста в этом цикле
ПЕРЕПРИСВАИВАЕТСЯ (`Z={...Z,messages:...}`), поэтому мутация «того же»
объекта не гарантирует видимости у исполнителя. Ключ по id вызова
снимает вопрос тождества объектов целиком.

Освобождение: запись удаляется читателем (врезка 3) сразу после чтения;
дополнительно — обрезание карты при превышении 64 записей.

## Врезка 2 — мост к движку одиночного запроса (ОТБРОШЕНА)

> Отброшена: движок вызывается с конструкторами из области видимости другого
> модуля, дотянуться до него можно было бы только ленивым мостом, который
> может никогда не инициализироваться. Вместо него — прямой HTTP-запрос,
> не зависящий ни от одной минифицированной привязки.

Движок (уникален в бандле):

    async function UHe({messages:e,systemPrompt:t,thinkingConfig:r,tools:n,signal:o,options:i})

Он идёт через ту же фабрику клиента, что и главный луп, значит наш патч
маршрутизации уводит любую не-`claude` модель в прокси автоматически.

Мост определяется НЕ рядом с `UHe`, а рядом с ГОТОВЫМ ОБРАЗЦОМ вызова
(модуль автореакции на комментарии артефактов), потому что там в области
видимости уже есть все конструкторы. Образец, дословно:

    await UHe({messages:[hn({content:i})],systemPrompt:am([rcv]),
      thinkingConfig:{type:"disabled"},tools:[],
      signal:e.context.abortController.signal,
      options:{model:RO(),querySource:"artifact_comment_triage",
        isNonInteractiveSession:!0,agents:[],hasAppendSystemPrompt:!1,
        mcpTools:[],enablePromptCaching:!1,maxOutputTokensOverride:128,
        stickyBetas:DF(ID()),proactivityLevel:Mre(e.context),
        agentContext:NS(),async getToolPermissionContext(){return ZH()}}})

Правка: сразу после этого выражения (или перед функцией, его содержащей)
определить:

    globalThis.__ccJudgeAsk = async (msgs, sys, model, signal, ctx) => UHe({
      messages: msgs, systemPrompt: am([sys]),
      thinkingConfig: {type:"disabled"}, tools: [], signal,
      options:{ model, querySource:"artifact_comment_triage",
        isNonInteractiveSession:!0, agents:[], hasAppendSystemPrompt:!1,
        mcpTools:[], enablePromptCaching:!1, maxOutputTokensOverride:512,
        stickyBetas:DF(ID()), proactivityLevel:Mre(ctx),
        agentContext:NS(), async getToolPermissionContext(){return ZH()} }});

ОТКРЫТО: допустимо ли произвольное значение `querySource`. Пока
переиспользуется значение образца — проверить на живом запуске, что оно
не влияет ни на что, кроме телеметрии.

## Врезка 3 — сам судья, перед исполнением инструмента

Место (2.1.235, дословно):

    se=await e.call(E,{...n,toolUseId:t,userModified:X.userModified??!1},o,i,p)

Соответствие имён в этой области: `e` инструмент, `t` id вызова,
`n` контекст инструмента, `i` сообщение ассистента (одноблочное),
`E` вход инструмента, `X` результат конвейера разрешений.
Рядом стоят устойчивые якоря: лог `[Stall] tool_dispatch_start`
(уникален по всему дереву) и ветка `phase:"pre_call"`.

Правка: перед этим выражением вставить блок, который
1. выходит немедленно, если не задана переменная окружения-выключатель;
2. выходит, если имя инструмента не `Agent` и не `Task`;
3. выходит, если вызов сделан НЕ главным лупом
   (`n.agentContext?.agentType !== "main"`);
4. собирает контекст: `(n.messages ?? []).concat(снимок хода по ключу t)`;
5. зовёт `globalThis.__ccJudgeAsk` с судейской системной частью и
   собственным таймаутом;
6. применяет вердикт:
   - подмена: `E = {...E, model: <модель>}` (проверено живьём, что
     параметр вызова сильнее модели из определения агента);
   - отказ: вернуть результат-ошибку тем же способом, что ветка
     `phase:"pre_call"`;
7. при ЛЮБОЙ ошибке, таймауте или неразборчивом ответе — пропускает
   вызов без изменений (fail-open) и пишет причину в отладочный лог.

## Инварианты, которые патч обязан держать

- Выключен по умолчанию: без переменной окружения поведение
  байт-в-байт как сегодня.
- Судья не судит сам себя: его собственный запрос инструментов не
  вызывает (`tools: []`), рекурсия невозможна.
- Субагенты не судятся (условие 3) — требование юзера.
- Fail-open на всех путях отказа.
- ~~Никакого чтения диска: контекст берётся из памяти.~~ ОТМЕНЕНО: настройка

## Смена решения 2026-08-20: отмена вместо подмены

Судья НЕ переписывает диспатч. При отрицательном вердикте он ОТМЕНЯЕТ вызов и
объясняет главному лупу, что не так; главный луп переделывает вызов сам.

Почему так, а не подмена модели: детерминированный гейт стоит РАНЬШЕ в той же
функции, поэтому подменённая здесь пара модель/усилие не прошла бы ничьей
проверки. Отказ строго уже того, что гейт уже разрешил, — порядок перестаёт
иметь значение.

Механика отказа — `throw` внутри блока, который и так обёрнут внешним
`catch(Z)` исполнителя инструментов. Прочитано в 2.1.235: этот catch строит
`{type:"tool_result", content:<текст ошибки>, is_error:!0, tool_use_id:t}` и
кладёт в поток сообщений. Текст отказа доходит до модели штатным путём, и патч
не сцеплен ни с одним минифицированным именем конструктора.

Собственный `catch` судьи fail-open по замыслу (упавший судья не должен
останавливать сессию), поэтому отказ помечается `__er.__ccJudgeBlock=!0` и
перебрасывается — иначе он гасился бы там же, где гасятся сбои канала.

Словарь вердиктов: `OK:` пропустить, `WARN:` пропустить с замечанием,
`BLOCK:`/`STOP:`/`DENY:` отменить. Отмена действует только при
`CLAUDE_JUDGE=enforce` или `enforce:true` в config.json.

## Дефекты, найденные и исправленные по ходу

1. `join("\n")` в исходнике патча эмитировался НАСТОЯЩИМ переводом строки
   внутри строкового литерала - бандл переставал разбираться, при этом все
   проверки по образцам оставались зелёными.
2. Дымовой прогон конвейера был написан как
   `echo "Version: $("$BIN" --version | head -1)"` - код возврата выбрасывался,
   и нерабочий образ отчитывался успехом. Теперь это жёсткий гейт: статус
   захватывается отдельно, отсутствие строки версии останавливает конвейер до
   подмены лаунчера.
3. Отказ гасился собственным `catch` судьи (см. выше).
4. Не-ASCII литерал приезжал в двойной кодировке: tweakcc распаковывает и
   пакует бандл как БАЙТЫ. Текст отказа эмитируется `\uXXXX`-экранированием.
5. Пропущенный `+` в склейке строк патча: автоподстановка точки с запятой
   делает такой код валидным для `node --check`, но обрывает строку патча.
   Поймано только дымовым гейтом - он и есть настоящая проверка.
6. Пустой вердикт было не отличить от отказа канала. При отладке сырой ответ и
   HTTP-статус пишутся в `last-response.json`.

## Журнал консультаций (добавлен 2026-08-20)

WARN до модели НЕ доходит и дойти не может: вызов идёт дальше, а результат
инструмента, который модель увидит потом, приходит от самого агента. Канала для
замечания там нет. Практически WARN — это OK с записью в журнал.

Поэтому журнал ведётся всегда, а не только при отладке: пропущенный по сбою
вызов и вызов, которого судья вовсе не касался, снаружи неотличимы («выключен
на обоих концах»). Файл `journal.jsonl`, строка на консультацию, поля:
`t`, `tool`, `agent`, `model`, `http`, `outcome`, `verdict`/`reason`.

`outcome`: ok | warn | block | block_not_enforced | empty | skip.
`block_not_enforced` выделен отдельно, иначе отказ, вынесенный вне режима
enforce, сливался бы с ok.

Запись объявлена ВНЕ внутреннего try, поэтому переживает сбой импорта и обрыв
канала; сама обёрнута так, что не может уронить вызов. Проверено на живых
прогонах с ВЫКЛЮЧЕННОЙ отладкой: обычный вызов дал `ok` с вердиктом, вызов на
мёртвом адресе — `skip` с кодом причины, агент при этом отработал.

Метрика первой очереди при живой эксплуатации — доля `skip` и `empty` по кодам
причин. В конвейер добавлена отдельная проверка наличия журнала.

## Селектор вызовов (добавлен 2026-08-20, по умолчанию отсутствует)

Что точка врезки видит (измерено живым прогоном, не выведено):
`{description, prompt, subagent_type, run_in_background}`. Поле `model`
присутствует, ТОЛЬКО если модель названа в самом вызове; при наследовании из
определения агента его нет вовсе. Значит правило «дорогая модель» задаётся
через ИМЯ агента, а не через модель.

`config.json.filter`: `classes_judge`, `classes_skip`, `agents_judge`,
`agents_skip` — списки регулярных выражений. `_skip` сильнее; если задан хотя
бы один `_judge`, судятся только совпавшие. Класс берётся из `[dispatch-class:…]`
в промпте. Отсутствие ключа `filter` = судить всё (прежнее поведение).

Отфильтрованный вызов пишет в журнал `outcome:"filtered"` и НЕ идёт в сеть —
налог задержки на нём нулевой, а экономия измерима по журналу.

Анти-луп держится структурно: судятся только вызовы с `agentType==="main"`,
поэтому диспатчи самих субагентов не судятся и рекурсии нет.

Проверено тремя прогонами: без фильтра — `ok`; фильтр на analysis/critique/audit
и класс scout — `filtered` (без обращения к сети); тот же фильтр и класс
critique — консультация состоялась, судья вынес отказ по существу (критик на
механической задаче), записанный как `block_not_enforced`.

## Попутно: код 429 от прокси

Пустой вердикт, ранее выглядевший как «модель промолчала», оказался ответом
HTTP 429. Виден в журнале как `outcome:"empty"` с `http:429`. Пример того,
зачем нужен сырой ответ: по одному лишь вердикту отказ канала и молчание модели
неотличимы.

## Сужение причин до их условий (2026-08-20)

Линза: не «печатает ли пропуск причину», а «совпадает ли УСЛОВИЕ пропуска ровно
с названной причиной или оно шире». У себя нашлось два места, где шире.

1. `outcome:"filtered"` покрывал два разных решения: класс назван в списке
   пропуска — и класс просто отсутствует в списке «судить». Второе — это то,
   как незамеченная опечатка в конфиге молча выключает судью для целого класса.
   Добавлено поле `by`: `classes_skip` | `agents_skip` | `not_in_judge_list` |
   `no_class_marker`.
2. Провал записи в журнал глушился собственным перехватом, то есть
   непроведённая консультация выглядела как непроисходившая — журнал
   воспроизводил ту самую слепоту, ради которой заведён. Теперь строка целиком
   уходит в поток ошибок.

Проверено: `by:"classes_skip"` и `by:"not_in_judge_list"` на живых прогонах;
при несуществующем каталоге журнала в поток ошибок ушла полная запись с ENOENT.

Две пробы до этого были негодными и переделаны — фиксирую, чтобы не повторять:
(1) вызов с классом `adjudication` до судьи не доходит, его отклоняет таблица
маршрутизации самого главного лупа; (2) `chmod 500` на КАТАЛОГ не мешает
дописывать в уже существующий файл — нужен несуществующий каталог.

  вердикт ссылается на первый вызов — раскладка хода по идентификатору работает.

ВЫКЛЮЧЕННОЕ СОСТОЯНИЕ (патч в образе, гвард снят) — проверено отдельно:
- переменной `CLAUDE_JUDGE` нет: обращений к каналу нет (проверено приёмником

## Перенос настроек tweakcc в наш патч (2026-08-20)

Патчи tweakcc на 2.1.237 не применяются целиком (её собранный бандл не
разбирается), поэтому четыре нужные настройки сделаны иначе.

1. `increaseFileReadLimit` — БЕЗ правки байтов. В 2.1.237 есть штатная
   переменная `CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS`, которая перебивает
   умолчание `eaS=25000` (функция `Amt`, ветка `taS()??…`). Вписана в
   `~/.claude/settings.json` со значением 1000000. Отдельный предел по БАЙТАМ
   `WAt=262144` переменной не управляется и остаётся: файл крупнее 256 КБ
   срезается независимо от токенного лимита.
   Проверено: файл 198 КБ без переменной обрывается на строке 759, с
   переменной дочитывается до маркера конца.
2. `statuslineThrottleMs` (шаг 23) — константа задержки планировщика статусной
   строки 300 -> 500. Локатор — место вызова `setTimeout(…, CONST)` внутри
   планировщика, оно же и называет константу.
3. `allowBypassPermissionsInSudo` (шаг 24) — снимаются ОБА отказа при euid 0:
   встроенный на пути запуска и экспортируемый `refuseBypassUnderRoot`. tweakcc
   правит только первый (её `String.match` останавливается на нём), то есть её
   вариант оставлял настройку наполовину применённой.
4. `claudeMdAltNames` (шаг 25) — обёртка вокруг ЕДИНОЙ функции чтения файла
   памяти: если по пути `…/CLAUDE.md` ничего нет, пробуются AGENTS.md,
   GEMINI.md, CRUSH.md, QWEN.md, IFLOW.md, WARP.md, copilot-instructions.md.
   Подход tweakcc (правка блока перехвата ошибок) здесь промахивается: при
   хранилищном дескрипторе отсутствующий файл возвращается штатным `absent`, не
   исключением. Для альтернативы дескриптор НЕ переиспользуется — он именует
   один ключ и вернул бы байты CLAUDE.md под чужим именем.
   Проверено с отрицательным контролем: каталог только с AGENTS.md — старый
   образ отвечает «НЕТ», новый читает и выполняет инструкцию из файла.

ЛОВУШКА, пойманная здесь же: первая версия проверки конвейера искала
`var X=500` и давала ЗЕЛЁНЫЙ на ЧИСТОМ образе — там шесть таких констант.
Проверка привязана к месту вызова. Все три новые проверки прогнаны против
чистого образа и корректно падают.

В `~/.tweakcc/config.json` эти четыре пункта выключены (резервная копия рядом),
чтобы при починке tweakcc они не применялись дважды.
