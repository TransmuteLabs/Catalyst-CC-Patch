## 1. `__num` — допустимое множество вместо двух проверок (K-1, K-9)

Сейчас (`tweakcc-patch.js:2354-2360`):

    '__num=(__k,__v,__d,__min,__q)=>{if(__v===void 0||__v===null||__v==="")return __d;' +
      'let __x=Number(__v);' +
      'if(!Number.isFinite(__x)||__x<__min){' +

Два пропуска: **тип** (`Number(true)===1`, `Number([])===0`, `Number([7])===7`)
и **верхняя граница**.

Получить: шестой параметр `__cap` (не обязателен) и типовой вход.

* Число берётся только из `typeof __v==="number"`, либо из строки:
  `typeof __v==="string"&&__v.trim()!==""?Number(__v):NaN`. Всё прочее — `NaN`,
  то есть уходит в ветку отказа с дефолтом.
* Отказ также при `__cap!==void 0&&__x>__cap`.
* Строка журнала называет ОБЕ границы:
  `"bad-setting:"+__k+"="+__clip(__v,24)+" (need "+__min+".."+(__cap===void 0?"inf":__cap)+"), using "+__d`.
  `__clip` (`:2403`) уже начинается с `String(__s??"")` — нестроковый вход он
  переживает; проверить это перед правкой и, если это не так, вернуть BLOCKED.

## 2. Потолок там, где значение уходит в `setTimeout` (K-1)

`__ms` доезжает до `'__to=setTimeout(()=>{__mine=!0;__ac.abort()},__ms);'`
(`:3213`), а `setTimeout` при значении > 2^31−1 сжимает задержку до 1 мс —
журнал при этом печатает ЗАПРОШЕННОЕ число (`:3286`, `"our cap "+__ms+"ms fired"`).

Три чтения обязаны получить `__cap = 2147483647`:

* `:3206` `'let __tmo=__num("timeout_ms",__o.tmoEnv||__cfg.timeout_ms,8000,1);'`
* `:3387` `'__num("rung.timeout_ms",__e.timeout_ms,__tmo,1),__e);'`
* `:3420` `'let __rt=__num("rung.timeout_ms",__e.timeout_ms,__tmo,1);'`

Пятый параметр (`__q`, тихо) у них сейчас не задан — передать `!1`, чтобы шестым
встал `__cap`. Других `__num`, чьё значение уходит в `setTimeout`, в файле нет:
проверить `grep -n setTimeout tweakcc-patch.js` и, если появится четвёртый, —
строкой в отчёт.

## 3. `max_tokens = 0` — «негодное», а не «ручки нет» (K-8)

Сейчас (`:3190-3191`):

    'let __mt=__e.max_tokens||__cfg.max_tokens;' +
    'if(__mt)__obj.max_tokens=__num("max_tokens",__mt,__obj.max_tokens??__mtd,1);' +

Ноль ложен: он не доходит до `__num`, и в живом шаблоне остаётся 1200, а без
шаблона тот же ноль даёт 8000 С объявлением — два ответа на одно значение.

Получить: наличие проверяется `??`, а не истинностью.

* `'let __mt=__e.max_tokens??__cfg.max_tokens;'`
* `'if(__mt!==void 0&&__mt!==null)__obj.max_tokens=__num("max_tokens",__mt,__obj.max_tokens??__mtd,1);'`
* Те же `__e.max_tokens||__cfg.max_tokens` в четырёх других местах — `:3195`,
  `:3210`, `:3243`, `:3251` — заменить на `__e.max_tokens??__cfg.max_tokens`.

После правки `max_tokens = 0` в обоих случаях становится НАЗВАННЫМ негодным
значением (`bad-setting`), а разные дефолты остаются разными законно: у шаблона
свой потолок, и он объявлен.

## 4. Булевы ручки — только boolean, негодное идёт в безопасную сторону (K-2)

Получить: общий читатель, объявленный в ТОМ ЖЕ списке деклараций, где живёт

## 7. `context_chars` ниже 60 — отказ вместо молчаливого пола (K-6, ядро)

`__cut` тянет к `__b = max(60, __n)`, а фаза маркера гонится за `__n`: при
`context_chars < 60` они расходятся. Пол поднимается К ЧИТАТЕЛЮ:

* `:2987` `'let __max=__num("context_chars",__cfg.context_chars,60000,0);'` → `,60);`
* `:3386` `'__cut(__num("rung.context_chars",__e.context_chars,__max,0)):__ctx,'` → `,60)`

`Math.max(60,...)` внутри `__cut` остаётся, но его комментарий переписать: через
конфиг эта ветка больше недостижима, она держит только прямые вызовы.

## 8. Горизонт записей — ядро называет ДОПУСТИМОЕ (L-6)

Сейчас (`:2535`): `'.filter((__x)=>__x!==__n&&!__x.endsWith(".gz"));'`

Отрицательный список не знает имён, которых ещё не придумали: `compact.py`
кладёт рядом `<имя>.json.gz.tmp.<pid>`, и он считается ГОРЯЧЕЙ ЗАПИСЬЮ — окно
`records_keep=N` вытесняет настоящую запись ради чужого обломка.

Получить: `'.filter((__x)=>__x!==__n&&__x.endsWith(".json"));'`

Инвариант после правки — ДВА утверждения, оба обязаны быть показаны стендом:
в окне остаётся ровно N файлов `*.json`, и посторонняя форма не считается И НЕ
УДАЛЯЕТСЯ (сегодня ядро способно снести tmp `compact.py` в миг между его
верификацией и `os.replace`).

## 9. Запись пробы — конечное имя только после полной записи (L-3)

Сейчас (`:2498`): `'await __jfs.writeFile(__jdir+"/records/"+__n,__out);'` —
`writeFile` создаёт/обрезает сразу конечное имя, и смерть посреди записи
оставляет файл, который следующий `validate.py run` принимает за запись и падает
на нём разбором.

Получить: запись в `records/<имя>.part.<pid>` и `rename` в конечное имя.
`process.pid` в образе доступен. При неудаче `rename` — существующая ветка
`record write failed` (её текст не менять). Промежуточная форма невидима
прополке ядра после правки 8 — назвать это в комментарии как связь двух правок.

## 10. Граница строки в журнале (L-9)

Сейчас (`:2582-2586`) — голый `appendFile(__r+"\n")`. Оборванный предыдущий
писатель оставляет хвост без `\n`, и следующая ПОЛНОЦЕННАЯ запись приклеивается
к обломку: построчный читатель теряет ОБЕ.

Получить: перед append писатель восстанавливает границу — если файл непуст и
последний байт не `\n`, полезная нагрузка предваряется `\n`. Форма (внутри
существующего `try`, до `appendFile`, с сохранением ветки `ENOENT`+`mkdir`):

    'let __pfx="";try{let __st=await __jfs.stat(__jdir+"/journal.jsonl");' +
      'if(__st.size>0){let __fh=await __jfs.open(__jdir+"/journal.jsonl","r");' +
        'try{let __b1=Buffer.alloc(1);' +
          'await __fh.read(__b1,0,1,__st.size-1);' +
          'if(__b1[0]!==10)__pfx="\\n"}finally{await __fh.close()}}}' +
    'catch{}' +

и далее `appendFile(..., __pfx+__r+"\\n")` в ОБОИХ вызовах (основном и после
`mkdir`). Толерантный читатель на стороне python остаётся: он теперь ловит ровно
то, для чего заявлен, — ОДНУ потерянную строку.

## Зубы (обязательная часть работы, не приложение)

Каждое утверждение выше принимается только с НАЗВАННОЙ мутацией, которая красит
СВОЙ сценарий СВОЕЙ причиной. Стенды кита: `tests/` (найти существующий стенд
ядра по `grep -rl "records_keep\|__num" tests/`) — новые сценарии дописывать в
него, новый стенд не заводить.

Обязательные сценарии (минимум по одному на правку):

1. `timeout_ms = 2147483648` → применённое значение равно дефолту 8000, в
   `__deg` есть `bad-setting:timeout_ms=2147483648 (need 1..2147483647)`.
2. `timeout_ms = true` → то же (тип), НЕ единица.
3. `max_tokens = 0` **на живом шаблоне `body.json`** — сценарий с шаблоном
   обязателен: прежний стенд гонял без него и потому дефект не видел.
4. `enforce = 1` → гейт ВКЛЮЧЁН + `bad-setting:enforce=1 (need true/false)`.
5. `CLAUDE_JUDGE=0` → проба выключена; `CLAUDE_JUDGE=enforce` → включена и
   отменяет.
6. `live_kinds = []` → пустой список принят И объявлен.
7. `context_chars = 30` → дефолт 60000 + `bad-setting`.
8. Прополка: каталог из N `*.json` + один `x.json.gz.tmp.999999` → остаются ВСЕ
   N `*.json` (кроме положенного вытеснения) И tmp НЕ удалён. Два утверждения —
   два сценария.
9. Смерть посреди записи оставляет `.part.<pid>`, а не конечное имя.
10. Журнал: хвост-обломок без `\n` + следующая запись → ДВЕ физические строки,
    из них одна разбирается (обломок), а новая запись цела.

**Мутация, которая падает с ошибкой (crash), не считается покраснением** — если
сценарий краснеет от того, что мутант не собрался, это код 2 «прибор не мерит»,
а не зелёный зуб. Мутация обязана быть РАВНОЙ ПО ДЛИНЕ форме, меняющей смысл.
