# Волна 40a — приборы должны мерить одно и то же на обеих платформах

Дерево: `Catalyst-CC-Patch`, HEAD `418b961`, ветка `main`.

## Зачем эта волна

Предполёт свипа (зонд пути сборки 600 с + стенд корпусных инструментов 929 с)
гоняется на локальной машине о 12 ядрах при load average 32, хотя предмет обеих
батарей — САМ КИТ, а не собираемая версия. На 32-ядерном воркере та же батарея
идёт 123 с вместо 929 с. Перенос упирается в одно: на Linux три сценария из 144
красные, и пока не назван их владелец, неизвестно, меряет воркер тот же предмет
или другой.

Диагноз снят двумя дорожками и проверен контроллером лично. Владельцы названы:
ОДИН настоящий дефект кита и ДВА дефекта приборов самого стенда. Плюс найден
класс шире исходного вопроса — самопроверка стенда засчитывает зубы без
положительного контроля.

Эта волна чинит ПРИБОРЫ. Пока прибор врёт, вердикт о платформе недействителен —
поэтому платформенная ось (волна 40b) идёт ПОСЛЕ, а не параллельно.

## Общие правила

- Ничего не коммитить. Изменения остаются в рабочем дереве; коммитит
  контроллер пофайловым pathspec после личной вычитки.
- Область записи — только файлы, перечисленные в «paths» ниже. Замеченное вне
  области — строкой в отчёт, не правкой.
- Комментарии в этом ките — полные, не только констрейнты (правило семьи для
  скриптов и патчей). Держать стиль соседних блоков: что за граница, почему не
  иначе, чем поймано. Существующие комментарии не удалять.
- Ни одна проблема не легализуется. Никаких «принять ограничение», заглушек,
  пинов на сломанное поведение.
- Числа в доках НЕ переписывать по расчёту: если счёт сценариев или мутаций
  изменится, снять его ПРОГОНОМ и вписать измеренное. Гейт чисел это проверяет.
- Exit-код снимать без пайпа либо с `set -o pipefail`.
- НЕ трогать: `~/.tweakcc`, `~/.claude`, `~/.local/bin/claude`, демон
  `target-warden`. Не убивать процессы, которых не запускал сам.
- Стоп-правило: неожиданное падение или расхождение с этим брифом — одна
  честная попытка, затем СТОП с сырым выводом. Диагностику не углублять.
- Если посылка брифа ложна — доказать командой и сказать прямо. Фабриковать
  дифф под формулировку запрещено.

## Предмет 1 — `stat -f %m` с пробелом ОТРАВЛЯЕТ вывод, а не отказывает

### Замеренный факт

У BSD `stat` ключ `-f` берёт ФОРМАТ следующим словом. У GNU coreutils `-f` —
это `--file-system`, аргумента он не берёт, поэтому `%m` становится ФАЙЛОВЫМ
операндом. GNU stat падает на нём (rc=1), НО ПЕРЕД ПАДЕНИЕМ ПЕЧАТАЕТ В STDOUT
статистику файловой системы по второму операнду. rc=1 запускает запасную ветку,
и её вывод ДОПИСЫВАЕТСЯ к этой каше.

Замер одной и той же функции на обеих машинах:

```
LINUX:  m=[  File: "kitd"
    ID: 97f00000000 Namelen: 255     Type: xfs
Block size: 4096       Fundamental block size: 4096
Blocks: Total: 496362701  Free: 161656367  Available: 161656367
Inodes: Total: 198642048  Free: 187765975
1788824969]                                              rc=1
macOS:  m=[1788824971]                                   rc=0
```

Идиома «попробуй BSD, иначе GNU» здесь НЕ деградирует безопасно. Разделитель
между отказом и отравлением — ПРОБЕЛ после `-f`: форма `-f%i` без пробела даёт
недопустимую опцию, пустой stdout и честный переход на запаску.

### Ценз, знаменатель 3 — все места перечислены

1. `tools/sweep.sh:387`
   `m=$(stat -f %m "$1" 2>/dev/null || stat -c %Y "$1" 2>/dev/null) || return 1`
   Дальше `[[ "$m" =~ ^[0-9]+$ ]]` (`:388`) не проходит → `return 1` →
   «метка не из будущего». Второй предикат `find -maxdepth 0 -mtime +0`
   (`:394`) на будущей метке пуст на ОБЕИХ машинах. Итог: ПРОПОЛКА ОБЛОМКОВ С
   МЕТКОЙ ИЗ БУДУЩЕГО НА LINUX МОЛЧА ВЫКЛЮЧЕНА.
2. `claude-patch-all.sh:583`
   `printf '%s\t%s\n' "$(stat -f '%m' "$entry" 2>/dev/null || stat -c '%Y' "$entry" 2>/dev/null || echo 0)" "$entry"`
   ТА ЖЕ болезнь (пробел есть). На Linux в КЛЮЧ СОРТИРОВКИ попадает
   четырёхстрочная каша плюс число. Это стадия «Cleaning old unpacker builds
   (keeping the pin in use + N most recent)» — то есть неверно упорядочивается
   то, ЧТО УДАЛЯЕТСЯ. Высокая важность: путь удаления.
3. `tools/build-path-probe.sh:2188`
   `stat -f%i "$1" 2>/dev/null || stat -c%i "$1" 2>/dev/null || echo "none"`
   БЕЗОПАСНО (пробела нет), но форма всё равно опирается на код возврата
   отравляющей команды — привести к общему носителю.

### Что сделать

Один НОСИТЕЛЬ чтения времени и inode, выбирающий ветку ПО ПЛАТФОРМЕ, а не по
коду возврата. Решение принято, не обсуждается: ветка выбирается один раз по
`uname -s` (`Darwin` → BSD-форма, иначе GNU-форма), результат обязан быть
единственной строкой из цифр, иначе — честный отказ вызывающему.

Носитель кладётся туда, откуда его видят все три потребителя. `tools/sweep.sh`
и `claude-patch-all.sh` — разные точки входа, поэтому носитель — отдельный
файл в `tools/`, подключаемый источником, по образцу уже существующего
`tools/tw-layer.sh` (посмотреть, как он подключается, и повторить механику).

В носителе — комментарий-констрейнт: пробел после `-f` и есть разделитель
между отказом и отравлением, поэтому форма «попробуй BSD, иначе GNU» здесь
запрещена навсегда.

### Зубы

На КАЖДОЕ из трёх мест — сценарий стенда, краснеющий при возврате отравляющей
формы, и мутация самопроверки с собственной причиной. Сценарий S12 уже есть
(`tools/corpus-tools-bench.sh:2775-2803`) и после правки обязан зеленеть на
обеих платформах; для места 2 (сортировка удаляемого) сценария нет — завести.

## Предмет 2 — самопроверка засчитывает зуб без положительного контроля

### Замеренный факт

`tools/corpus-tools-bench.sh:4898-4933`, `self_check()`: строит свежий кит и
корпус, применяет мутацию, гоняет сценарий, и если `FAILED` вырос И `LAST_EVID`
содержит `MUT_CAUSE[n]` — засчитывает «покраснила своей причиной».

КОНТРОЛЬНОГО ПРОГОНА БЕЗ МУТАЦИИ ТАМ НЕТ. Поэтому если сценарий красен в
базовом прогоне ТЕМ ЖЕ следом, мутация получает зачёт ни за что.

Живой случай (Linux):
```
ПРОВАЛ 97 S12 обломок с меткой из будущего не убирается прополкой
ok     мутация 101 покраснила сценарий 97 своей причиной
```
Мутация 101 — единственная, целящаяся в S12; сценарий 97 на Linux и без неё
красен ровно следом `БУДУЩАЯ_МЕТКА_ОСТАЛАСЬ` (`:2796`). Совпадение по строке
есть, измерения нет.

Это КЛАСС, а не случай: так зеленеет любая мутация, чей ожидаемый след
совпадает с базовым отказом её сценария. На маке все 144 сценария зелены,
поэтому дыра невидима ровно до переноса.

### Что сделать

Образец правильного поведения уже есть в семье: `tools/checks-teeth.py:338`
печатает `checks-teeth: КОНТРОЛЬ без мутации: ЗЕЛЁНО (образ)`. Повторить эту
дисциплину в `self_check`:

- перед мутацией прогнать сценарий БЕЗ неё и потребовать ЗЕЛЁНОГО;
- если сценарий и так красен — это КЛАСС 2 «зуб НЕ ИЗМЕРЕН», отдельный и от
  «мутация прошла молча» (класс 1), и от «замена невалидна» (уже есть, `:4908`);
  в счёт покрасневших такой зуб НЕ идёт, и итоговая строка обязана называть их
  число отдельно.
- Итоговая строка самопроверки печатает три величины: сколько зубов измерено,
  сколько покраснело, сколько НЕ ИЗМЕРЕНО. Вердикт красен, если не измеренных
  больше нуля: молчаливый пропуск зуба неотличим от зуба, которого нет.

### Зубы

Мутация самопроверки на саму эту дисциплину: сделать сценарий красным в базе и
убедиться, что его зуб уходит в «не измерено», а не в «покраснел».

## Предмет 3 — S6: воркер опознаётся по `spawn_main`, которого при `fork` нет

### Замеренный факт

`tools/corpus-tools-bench.sh:2629`:
```bash
wpid=$(ps -eo pid,ppid,args | awk -v p="$cpid" '$2==p && /spawn_main/ {print $1; exit}')
```
намерение объявлено на `:2626` — «Воркер опознаётся по argv: spawn_main».

`spawn_main` попадает в argv воркера ТОЛЬКО при методе старта `spawn`. Кит
метод старта нигде не пинит (ценз по `set_start_method|get_context|forkserver`
дал ноль при положительном контроле — `ProcessPoolExecutor` находится
на `tools/checks-teeth.py:47` и `:362`). Значит решает умолчание платформы:

```
macOS  python3 3.14.7: spawn  → 984 ... spawn_main(tracker_fd=9, ...) --multiprocessing-fork
LINUX  python3 3.12.14: fork  → 981519 python3 /tmp/mpprobe.py     (argv РОДИТЕЛЯ)
```

Половина `$2==p` того же awk ребёнка НАХОДИТ — ложен только предикат
`/spawn_main/` (это положительный контроль пустого результата). Цикл `:2628`
выжигает весь бюджет (300 × 0.1 с = 30 с) и падает на `:2637`.

Сам кит здоров: при опознании по ppid тот же прогон даёт
```
checks-teeth: КОНТРОЛЬ без мутации: ЗЕЛЁНО
checks-teeth: НЕ МЕРИЛ -- воркер умер (SIGKILL/OOM), мутации не измерены
RC=2
```
— ровно то, чего требуют `:2649-2656`.

### Что сделать

Опознавать воркера пула по РОДСТВУ (ppid), а не по форме argv. Форма argv —
свойство умолчания CPython, а не пула: на Python 3.14 умолчание Linux
становится `forkserver`, и тот же детектор останется слеп и там. Родство
устойчиво ко всем трём методам старта.

Если по ppid находится больше одного потомка — брать по объявленному правилу
(назвать его в комментарии), а не «первого попавшегося».

Комментарий на `:2626` не удалять — переписать: он объявляет намерение, и
намерение меняется вместе с формой.

### Зубы

Мутация самопроверки, возвращающая опознание по argv, обязана покраснить S6
своей причиной.

## Предмет 4 — S10 и четыре родственных места: детектор находит САМ СЕБЯ

### Замеренный факт

`tools/corpus-tools-bench.sh:2736` (та же форма на `:2714`):
```bash
orph=$(ps -eo pid,args | awk -v r="$C/s95tmp" 'index($0, r) && /sleep 120/ { print $1 }')
```
Командная строка самого awk удовлетворяет ОБОИМ предикатам: путь приходит через
`-v r=<путь>`, а `sleep 120` стоит в тексте программы.

Замер, печатающий найденную строку целиком:
```
>> 1370556 awk -v r=/tmp/s10c/s95tmp index($0, r) && /sleep 120/ { print ... }
orph_seen = [1370607]  -> вердикт стенда: ПРОВАЛ
```
При этом кит отработал: `rc=143`, трап `build-path-probe.sh:2355-2357`
сработал, `cleanup` (`:2341-2344`) держателя снял и дождался — держателя нет
даже зомби.

Почему мак зелен: BSD awk (`awk version 20200816`) при `-v name=value` корёжит
собственный argv, и `ps` показывает `awk -v r ZZPATHZZ` БЕЗ текста программы;
GNU Awk 5.3.0 показывает всё. Перекрёстная проверка: голая регулярка находит
себя на ОБЕИХ платформах — значит дело именно в `-v`, а не в общем «соседей не
видно».

Это тот же урок, за который кит уже платил («`pgrep -f` находит себя»),
выживший только потому, что платформа его прятала.

### Что сделать

Детектор обязан исключать СВОЙ собственный процесс. Правка нужна во ВСЕХ
пяти местах этой формы, а не только там, где значение становится вердиктом:
`:2182`, `:2428`, `:2541`, `:2714`, `:2736`. В четырёх из них результат идёт в
`kill` — там самонахождение сегодня безвредно лишь по совпадению, и на
переиспользованном pid безвредным быть перестаёт.

Исключение по собственному pid — не по форме строки: фильтр по тексту сам
станет следующей ловушкой того же класса.

В комментарий — констрейнт: детектор процессов по форме командной строки
обязан исключать себя, и на маке эта ошибка невидима из-за BSD awk.

### Зубы

Сценарий, в котором держатель СНЯТ, обязан быть зелёным на обеих платформах;
мутация, снимающая исключение собственного pid, обязана его покраснить.
